# Site Spec Patterns

## First Rule

Extract principles, not surfaces.

This project can learn from a reference repository without copying its subject,
framework, or visual skin. The useful transfer is the structure of thinking.

## What To Extract Before Writing A Spec

### 1. Governing metaphor

This museum uses a guided exhibit metaphor.

A spec should state the metaphor clearly enough that layout, copy, and image
choices follow from it.

### 2. Project thesis

The thesis for this site is not only "retro handhelds existed." It is that
portable gaming devices should be read as preserved artifacts with technical,
cultural, and emotional meaning.

### 3. Main route

The current route is:

1. entrance hall
2. six chronological exhibit rooms
3. one-device spotlight sections inside those rooms

Later workstreams should preserve a clear spine rather than a loose pile of
pages.

### 4. Companion surfaces

Supporting surfaces may include:

- room pages
- collection notes
- regional comparisons
- preservation guides

Those should reduce overload, not compete with the main route.

### 5. Evidence model

For this museum, evidence includes:

- artifact images
- historical context
- key features
- cultural impact
- narrative placards
- scarcity/preservation notes

### 6. Process model

Each new feature should inherit the spec, sprint, and QA discipline.

## What A Strong Spec Should Answer

Every serious spec should make these clear:

- what problem the feature solves
- what the feature should feel like
- what the main visitor journey is
- what content model it needs
- what systems must be reusable
- how quality will be checked

## How To Split Work Into Sprints

Good sprint boundaries are product units, not random file groups.

Strong examples for this project:

1. entrance-hall foundation
2. chronology-hall expansion
3. shared exhibit template extraction
4. companion content surface such as collection notes
5. QA and consistency pass

Weak examples:

- adjust some CSS
- clean up the homepage
- finish the site

If a sprint does not produce one clearly reviewable outcome, it is probably too
wide.

## Minimal Checklist For New Specs

Before approving a spec, confirm that it names:

- the exhibit problem being solved
- the design metaphor
- the route through the material
- the required exhibit fields
- the verification model
- the sprint plan

## Main Lesson

The project should grow by preserving coherence, not by adding pages quickly.

Strong specs protect the museum from becoming a disconnected set of retro game
facts.
